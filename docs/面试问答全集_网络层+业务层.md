## 开场：怎么用 1 分钟介绍这个项目

**参考话术**：

> 我做的是一个**基于 Reactor 模型的高并发 HTTP 网关**，分两层：网络层和业务层。
> **网络层**是我自己实现的 Reactor 框架——EventLoop（one loop per thread）、Channel 封装 fd 事件、EpollPoller 做 IO 多路复用、TimerWheel 做连接超时管理，参考了 muduo 的设计思想。
> **业务层**是一个**双引擎的实时风控+限流系统**：请求进来先走风控引擎（特征提取→规则匹配→风险评分→四级决策），再走限流引擎（本地滑动窗口 + Redis 兜底）。目标是单机 10w QPS、P99 < 2ms，Redis 故障时自动降级放行。

**面试官最可能顺着问的三条线**：① 网络层 Reactor 细节；② 限流算法和一致性；③ 高可用降级。下面按这三条线展开。

## 第一部分：网络层 Reactor（★ 重点，现有文档盲区）

### 1. 你的 EventLoop 主循环是怎么工作的？

**答**：EventLoop 的核心是 `loop()`，一个 while 循环：每次先 `poller_->poll(timeout, activeChannels)` 阻塞等待事件，拿到就绪的 Channel 列表后，逐个调用 `channel->handleEvent()` 分发到对应的读/写回调；处理完一轮事件后，再执行 `doPendingFunctors()` 处理其他线程投递过来的任务。整个循环只有一个线程在跑，这就是 one loop per thread——一个线程配一个 EventLoop，EventLoop 和线程一一绑定。

**追问：poll 的超时时间怎么定？** 我设了 100ms，既不是死等（避免有 pending 任务时反应太慢），也不会太短导致空转浪费 CPU。实际上有 wakeup 机制兜底：即使 poll 在阻塞，别的线程也能通过 wakeup 把它唤醒，所以超时时间不用设太小。

---

### 2. one loop per thread 是什么意思？为什么这么设计？

**答**：就是一个线程独占一个 EventLoop，EventLoop 对象只在创建它的那个线程里运行，**线程和 loop 一一绑定**。这么设计最大的好处是：**不用加锁**。因为所有和这个 loop 相关的 Channel、回调都在同一个线程里执行，不存在多线程竞争同一份数据的问题，代码简单、性能高。跨线程要操作这个 loop 时，用 `runInLoop/queueInLoop` 把任务投递过去，而不是直接碰它的数据。

**追问：怎么保证"只在 loop 线程执行"？** `isInLoopThread()` 就是拿当前线程 id 和 loop 记录创建时的 `threadId_` 比，很多操作前面都有 `assert(isInLoopThread())`，在 Debug 下能抓出"在错误线程操作"的 bug。

---

### 3. runInLoop 和 queueInLoop 的区别？为什么要这两个？

**答**：都是"把一个任务交给 EventLoop 去执行"，但**runInLoop**：如果当前就在 loop 线程里，直接执行（不用排队）；不在就转成 queueInLoop。**queueInLoop**：把任务 push 进 `pendingFunctors_` 队列，然后唤醒 loop 线程，等它下一轮 poll 醒来后执行。

它们存在的原因：**跨线程调用必须线程安全**。比如某个连接在别的线程里要 `send`，不能直接操作 loop 里的数据，必须 `queueInLoop` 投递过去，让 loop 线程自己执行。这就是 Reactor 框架里"线程间通信"的标准做法。

**追问：queueInLoop 里为什么要 wakeup？** 因为 loop 线程可能正阻塞在 `poll` 上，如果不唤醒它，投递的任务要等到 poll 超时（100ms）才被处理，延迟太高。wakeup 能让它立刻醒来处理。

---

### 4. 你的 wakeup 机制是怎么实现的？（eventfd / socket pair）

**答**：wakeup 就是"让阻塞在 poll 的 loop 线程立刻醒过来"的机制。我在 EventLoop 里创建了一个 wakeup fd，把它也注册到 poll 里监听读事件。当别的线程 `queueInLoop` 需要唤醒 loop 时，就往这个 fd 写一个字节，poll 立刻返回，loop 醒来处理 pending 任务，同时把这个字节读掉（避免下次又触发）。

**跨平台差异**（这是我代码里实际处理的）：**Linux 上用 `eventfd`**，一个 fd 既能读又能写，简单高效；**Windows 上 eventfd 没有，我用了一对自连接的 socket**（一个 listener 连接自己，得到读端和写端两个 fd），写端发数据、读端就变成可读。这就是 `createWakeupPair()` 里 `#ifdef _WIN32` 分支干的事。

**追问：为什么不用管道？** eventfd 比管道更轻量——管道需要两个 fd 还涉及缓冲区，eventfd 一个 fd 就够了，语义也更纯粹（就是个计数器/信号量）。

---

### 5. Channel 是什么？它的生命周期怎么管理？

**答**：Channel 是"**一个 fd 及其事件回调的封装**"。它把 fd、感兴趣的事件（events）、实际发生的事件（revents），以及读/写/关闭/错误四个回调绑在一起。Poller 管的是"哪些 fd 有事件"，Channel 管的是"这个 fd 有事件了该干什么"。一个 fd 对应一个 Channel，Channel 不拥有 fd（fd 由 Socket/TcpConnection 管理），它只负责注册和回调。

**生命周期关键点**：Channel 里有个 `addedToLoop_` 标记，配合 `update/remove`，保证"注册到 poll"和"从 poll 移除"成对出现。TcpConnection 析构前要先 `channel_->remove()`，否则 poll 里还残留着这个 fd 的注册，会出问题。

---

### 6. 你的 EpollPoller 是怎么实现的？用的 LT 还是 ET？

**答**：EpollPoller 封装了 epoll 三个系统调用：`epoll_create` 建 epoll 实例，`updateChannel` 里用 `epoll_ctl` 注册/修改 fd 的事件，`poll` 里用 `epoll_wait` 等事件。我用的 **epoll 默认的水平触发（LT）**，没开 EPOLLET。

**追问：为什么用 LT 不用 ET？** LT 的语义是"只要 fd 还有数据没读完，就持续通知"，处理起来更简单、不容易漏数据（读多少算多少，没读完下次还会触发）；ET 是"只在状态变化时通知一次"，必须一次读完、配合非阻塞 IO，编码更复杂。对我要的"简单可靠"来说，LT 是更稳的选择。当然 ET 性能理论上略好（少几次通知），但 LT 已经完全够用。

**追问：epoll 为什么比 select 快？** 核心是**事件驱动 + 只处理就绪的**：epoll 用红黑树注册 fd（`epoll_ctl` 一次），事件就绪时通过内核回调把 fd 放进就绪链表，`epoll_wait` 直接取就绪的，复杂度只和就绪事件数有关；而 select 每次都要把全部 fd 从用户态拷到内核、O(n) 遍历所有 fd，连接一多就慢。

---

### 7. 你的 Buffer 为什么有 prependable（预留空间）？

**答**：我的 Buffer 是参考 muduo 的**三区结构**：`[prependable | readable | writable]`，用两个下标 `readIndex_` 和 `writeIndex_` 划分。**prependable 的作用是：能在头部预留空间，方便"往前面插数据"**。

典型场景：HTTP 响应要加"状态行 + 头部"，而头部长度事先不确定，可能要补。如果 Buffer 没有前置预留，往头部插数据就得把整个数据往后挪；有了 prependable，直接在头部加就行，O(1)。

**追问：readFd 读数据时怎么高效读？** 用的是 readv 配合栈上临时空间，先尝试把数据读到 writable 区，如果不够就用临时空间补，再统一 append，减少一次拷贝。核心思路是"尽量一次 read 系统调用读走尽量多的数据"。

---

### 8. TcpConnection 为什么继承 enable_shared_from_this？

**答**：因为 TcpConnection 的生命周期是**由 shared_ptr 管理的**（存在 TcpServer 的 `connections_` map 里），但它的回调里（比如 handleClose、handleRead）又需要"拿到指向自己的 shared_ptr"。如果直接写 `shared_ptr<this>` 会生成一个新的控制块，导致同一个对象被两个独立 shared_ptr 计数、最终 **double free**。继承 `enable_shared_from_this` 后，用 `shared_from_this()` 就能拿到和外界共享同一控制块的安全指针。

**追问：什么时候会用到 shared_from_this？** 最典型是 `handleClose()` 里：我要在回调里把自己从 TcpServer 的 map 里移除，如果移除的瞬间引用计数归零、对象被析构了，而我还在它的成员函数里执行，就是"自己删自己"的悬空问题。所以我先 `TcpConnectionPtr guard(shared_from_this())` 保一手，保证执行完回调前对象还活着。

---

### 9. 发送数据是怎么处理的？为什么要输出缓冲区？

**答**：`send` 分两层：`send()` 检查在不在 loop 线程，不在就 `runInLoop` 投递过去（保证线程安全）；`sendInLoop()` 里先尝试**直接 write/send**，如果一次没发完（内核发送缓冲区满了，返回 EAGAIN），就把剩下的数据放进**输出缓冲区 outputBuffer_**，然后**注册写事件**（enableWriting）。等内核缓冲区可写了，poll 触发写事件，`handleWrite` 再把 outputBuffer 里的数据继续发，直到发完，再关闭写事件。

**为什么需要输出缓冲区**：因为网络发送不保证一次发完（非阻塞 IO 下 EAGAIN 很常见），把发不完的数据缓存起来、等可写再发，就能做到"想发多少就发多少，底层慢慢发"，上层不阻塞。这是高并发服务器发送侧的标配设计。

---

### 10. 你的连接超时（TimerWheel）是怎么做的？

**答**：我用**时间轮（TimerWheel）**管理连接的空闲超时。时间轮就是一个环形数组，每个槽是一个定时任务链表，指针每秒走一格（tick）。连接建立时注册一个定时任务，收到请求时 `refreshTimeout` 刷新（把任务挪到更远的槽），如果连接一直没消息、超时了，就触发超时回调、关连接。

**追问：为什么用时间轮而不是每个连接一个定时器？** 海量连接下，如果每个连接一个 timerfd/定时器，数量太大；时间轮的插入、删除、刷新都是 O(1)（直接定位到某个槽的链表），非常适合"大量连接、周期性超时"的场景。缺点是精度是 tick 粒度（秒级），但连接超时秒级精度完全够用。

---

### 11. LoopThreadPool 是怎么做负载均衡的？

**答**：LoopThreadPool 创建 N 个子线程，每个子线程跑一个自己的 EventLoop（这就是 one loop per thread 的池化）。新连接到来时，用 **round-robin（轮询）** 方式 `getNextLoop()` 从这些子 loop 里选一个，把连接分配过去。这样多个连接分散到多个 loop、多个核上并行处理，充分利用多核。

**追问：为什么新连接要分配到子 loop，而不是全在主 loop 处理？** 如果全在一个线程处理，单核 CPU 会成为瓶颈，多核浪费了。分配到子 loop，每个 loop 独立跑在自己的线程上，无锁、可扩展。这也是"主从 Reactor"的简化版——主 loop 负责 accept，子 loop 负责处理连接读写。

---

### 12. 你为什么同时有 SelectPoller 和 EpollPoller？

**答**：这是**跨平台**的考虑。Linux 上用 EpollPoller（epoll 性能最好），Windows 上 epoll 没有，就用 SelectPoller（select，Windows 上 poll 也不完善）。在 EventLoop 里用 `#ifdef _WIN32` 条件编译选择用哪个，接口统一成 Poller 抽象基类（`poll/updateChannel/removeChannel` 三个虚函数），上层完全无感。

**追问：这体现了什么设计思想？** 面向接口编程 + 平台差异封装。上层只依赖 Poller 抽象，具体用 epoll 还是 select 是平台细节，隔离在实现层。面试时可以强调"接口统一、实现可替换"。

## 第二部分：业务层 风控 + 限流（提炼 + 补充追问）

### 13. 请求进来后的完整处理流程？（四阶段流水线）

**答**：请求进来后，`RateLimitService::process()` 走一条四阶段流水线：

1. **Phase 0 FastPath**：先查黑白名单（本地缓存 O(1)），白名单直接 ALLOW、黑名单直接 REJECT，**零网络、零计算开销**，把绝大多数正常/异常请求在最前面短路掉。
2. **Phase 1 特征提取**：提取风险信号（静态特征如 API 敏感度、时间风险；速度特征如 QPS、突发比例）。
3. **Phase 2+3 规则匹配 + 风险评分**：匹配风控规则，用评分器算出风险分，映射到四级决策。
4. **Phase 4 动作分发**：ALLOW 放行、LIMIT 收紧配额走限流、CHALLENGE 要求验证、REJECT 拒绝。

**追问：为什么黑白名单放最前面？** 因为它是**零成本短路**——白名单用户是可信的、黑名单是已知恶意的，都用不着再花时间提特征、算分。把最便宜、能最快下结论的判断放最前，是性能优化的第一原则（先过滤掉不需要深度处理的大头）。

---

### 14. 风控的评分机制是怎么算的？（规则分 + 特征分）

**答**：总分 = **规则触发分 + 特征贡献分**。规则触发是"定性"——请求特征满足了某条规则的触发条件（比如"qps > 50"），就获得这条规则的基础分×权重；特征贡献是"定量"——特征值本身也按权重贡献分数（比如 qps=50，贡献 50×0.3=15 分）。两者叠加，既判断了"是否异常"，又量化了"异常程度"。

**追问：为什么要"规则分 + 特征分"两部分，只用规则不行吗？** 不行。规则是二元的（触发/不触发），两个请求都触发了"高频"规则，规则分一样，但一个 qps=50、一个 qps=500，风险完全不同。特征分把这个"程度"补上了，让评分更精细。这是可解释风控系统（区别于黑盒 ML）的经典设计。

---

### 15. 为什么要有 CHALLENGE 这个级别，而不是直接 REJECT？

**答**：CHALLENGE 是**误杀缓冲带**。直接 REJECT 可能误杀正常用户——比如公司内网出口 IP 被标记、用户刚换了设备，这些"看起来可疑但其实是好人"的请求，如果一刀切拒绝，会伤害用户体验、产生投诉。CHALLENGE 让这类用户通过验证码自证清白：机器人过不了验证码、被拦截；正常用户输个码就能继续。**既拦截了机器，又减少了误杀**。这是"安全"和"用户体验"之间的平衡设计。

**追问：LIMIT 和 CHALLENGE 有什么区别？** LIMIT 是"允许通过但收紧配额"（比如正常 100 req/s 降到 10 req/s），用户无感知、只是变慢；CHALLENGE 是"要求用户主动验证"，用户要完成验证码才能继续。前者针对轻度异常，后者针对中度异常。

---

### 16. 你的本地滑动窗口限流是怎么实现的？

**答**：核心是 `LocalSlidingWindow`，用 `deque<uint64_t>` 存每个请求的**时间戳**。检查时：先**清理过期数据**（把窗口外的旧时间戳 pop 掉），再**判断当前数量是否 < maxReq**，没超就 push 本次时间戳、放行；超了就拒绝。这是精确的滑动窗口（毫秒级），没有固定窗口的"边界突刺"问题。

**追问：deque 存时间戳有什么缺点？** 如果窗口大、请求多，deque 会很长（比如 1 分钟 1 万请求就是 1 万个元素），内存和清理有开销。优化方向：用小窗口聚合（1 秒一个 bucket，60 个 bucket 组成 1 分钟），或者"计数器 + 窗口起始时间戳"。面试主动说出这个缺点 + 优化方向是加分项。

---

### 17. 本地限流和 Redis 怎么配合？为什么要 80% 阈值？

**答**：这是**本地优先 + Redis 兜底**的三层策略：

1. **安全区**：本地计数 < 80% 阈值 → 直接本地判断，**不查 Redis**（零网络开销）；
2. **警戒区**：本地计数 ≥ 80% → **查 Redis 精确校验**（因为本地计数在多机场景可能滞后，提前查 Redis 防止超限）；
3. **Redis 不可用** → **fail-open 放行**。

**为什么是 80%**：本地计数在多机部署下是滞后的（各机器各数各的，汇总到 Redis 有延迟）。如果等本地数到 100% 才查 Redis，可能已经超限了。80% 提前触发 Redis 校验，是"性能"和"不超限"之间的平衡点。

**追问：本地和 Redis 最终一致，怎么保证不超限？** 靠"警戒区提前查 Redis"兜底——真正接近阈值时以 Redis 的精确值为准。极端情况下（100ms 同步间隔内）可能轻微超限，但这是"最终一致"换性能的权衡，业务可接受。

---

### 18. 你的 Redis Lua 脚本做了什么？为什么必须用 Lua？

**答**：滑动窗口的 Redis 版用 Lua 脚本，五步操作：`ZREMRANGEBYSCORE` 清理窗口外旧数据 → `ZCARD` 计数 → 判断是否超限 → 未超则 `ZADD` 记录 → `EXPIRE` 设置过期。**为什么必须用 Lua**：这五步必须**原子**执行，否则有竞态——比如线程 A 数到 99 还没写，线程 B 也数到 99 也放行，最终超限。Lua 在 Redis 单线程里执行，天然原子；而且五步合成一次网络往返，性能也好。

**追问：为什么用 ZSet 不用 List？** ZSet 按 score 范围删除（`ZREMRANGEBYSCORE`）是 O(log N)，List 要遍历 O(N)，大窗口下 ZSet 更快。

---

### 19. 热点 key 分片是怎么回事？

**答**：如果一个热点用户（比如大 V）的 key 被所有请求打，单个 Redis key 会成为瓶颈（单 key 的读写热点）。我的做法是**分片**：把热点 key 拆成 16 个分片，每个请求**随机选一个分片**写入+检查，每个分片配额 = 总配额/16。这样热点压力被分散到 16 个 key 上，降到 1/16。

**追问：分片带来的误差怎么算？** 因为是随机选分片，理论上会有误差（比如 16 分片、总配额 100，某分片可能超过 100/16）。误差量级是 ±6.25%（1/16），对限流这种"软限制"场景完全可接受。这是个典型的"用一点点精度换性能"的权衡。

---

### 20. Redis 挂了，你的系统怎么保证可用？

**答**：三层降级：

1. **连接层熔断**：连续失败次数达到阈值就熔断，不再请求 Redis（避免大量请求堆积、超时）；
2. **限流层 fail-open**：Redis 不可用时**默认放行**，同时记录 degraded 计数（宁可放过，不可误杀正常流量——保证可用性优先）；
3. **风控层降级**：特征提取失败时填默认安全值，评分降低，甚至退化成"纯限流模式"。

**追问：fail-open 会不会被攻击者利用？** 会，这是**可用性和安全性的权衡**。fail-open 保证服务不挂，代价是 Redis 挂的窗口期攻击可能漏进来。生产上可以配置成 fail-close（挂了就全拒，安全但影响可用），或"本地严格限流"（挂了启用更严格的本地限流）。面试时讲清楚这个 trade-off 和可选策略，是生产意识的体现。

---

### 21. EventBus 是怎么设计的？队列满了怎么办？

**答**：EventBus 是**异步事件上报**，把风控决策事件（RiskEvent）从主链路解耦出来。主链路决策完，`publish` 把事件**非阻塞**投递到一个**有界队列**（容量 65536），后台单线程消费、更新 Metrics。**队列满了就静默丢弃**（tryPush 返回 false），绝不阻塞主链路——因为指标数据允许少量丢失（99.9% 准确率够用），而阻塞生产者会影响核心请求延迟（不可接受）。

**追问：为什么是单消费者（MPSC）？** 多个生产者（各请求线程）并发投递，但 Metrics 的更新如果多线程写会竞争，所以用一个消费者线程串行消费、更新，避免锁竞争。这是"多生产者单消费者"的经典模型。

---

### 22. 你的规则匹配为什么用责任链模式？

**答**：责任链把三种检查串成一条链：`WhitelistHandler → BlacklistHandler → DimensionHandler`。白名单命中直接短路（不再走后面的），黑名单命中短路，都没命中才去收集匹配的限流规则。**为什么用责任链而不是 for 循环 + if/else**：每种检查逻辑独立封装、可单独扩展（新增检查维度就加一个 Handler），链的顺序体现了优先级（白名单 > 黑名单 > 规则），符合开闭原则。这是责任链模式的典型应用场景。

---

### 23. LocalCache 为什么 1 秒刷新？shared_mutex 是怎么用的？

**答**：LocalCache 缓存规则快照（黑白名单、限流规则、风控规则），后台线程每 1 秒从 ConfigManager 拉一次全量快照。**为什么 1 秒**：太快（100ms）会让 ConfigManager 的锁成为瓶颈；太慢（10s）规则变更生效太慢；1 秒是工程平衡点（阿里 Sentinel 也是 1s）。

**shared_mutex 的用法**：读规则用 `shared_lock`（多个读线程**并发读**，互不阻塞——因为请求处理是读多写少），刷新时用 `unique_lock`（写线程**独占**）。这是典型的"读多写少"用读写锁优化的场景，比普通 mutex（读也互斥）并发度更高。

---

### 24. 你的监控指标是怎么设计的？

**答**：三层监控：① **基础计数器**（total/allow/limit/challenge/reject，全是 atomic 无锁）；② **规则命中计数**（ruleId → count，判断规则有没有生效）；③ **滑动窗口聚合**（最近 60 秒的拦截率，环形数组 60 个 bucket 每秒一格，O(1) 读写）。最后用 MetricsExporter 输出 **Prometheus 格式**，能被 Prometheus 直接抓取。

**追问：为什么滑动窗口用本地环形数组，不用 Redis ZSet？** 本地指标不需要跨机共享，环形数组 O(1) 比 ZSet 的 O(log N) 快，也没网络开销。这是"本地能解决的就不上 Redis"的原则。

## 第三部分：跨层综合追问（拉开差距的题）

### 25. 单机 10w QPS 是怎么做到的？

**答**：几个核心优化叠加：

1. **网络层用 epoll + Reactor**，一个线程监听海量连接，非阻塞 IO，多 loop 多核并行；
2. **黑白名单快速路径**，80% 的正常/异常请求在最前面 O(1) 短路；
3. **本地限流优先**，80% 流量走本地内存计数、不查 Redis（零网络开销）；
4. **Redis 连接池 32 条**，Lua 原子脚本减少往返；
5. **监控异步化**，EventBus 后台消费，主链路零阻塞。

**追问：10w QPS 是实测还是理论值？** （诚实回答）目前是**设计目标/理论值**，参考了 muduo 的基准，实际压测计划用 wrk 跑。这个诚实态度很重要——面试官一听就知道你是真做过还是吹的，别硬撑。

---

### 26. 这个项目最大的不足是什么？你怎么优化？

**答**（主动暴露不足 + 给方案，比被动等问好）：

1. **本地限流单 mutex 保护所有窗口**，高并发下可能成为瓶颈 → 优化：按 key hash 分片锁，或环形数组无锁化；
2. **EventConsumer 单线程**，消费量大时可能滞后 → 优化：批量消费、或多消费者分片；
3. **特征提取是串行的** → 优化：多个无依赖的 Extractor 用线程池并行；
4. **配置是内存单例、无持久化、无校验** → 优化：接入 etcd/Nacos、加配置校验；
5. **ML 评分器只是预留接口** → 优化：接入 ONNX Runtime。

主动讲不足 + 给方案，体现的是"我知道边界在哪、知道怎么改进"，这是高级候选人的信号。

---

### 27. 如果流量涨到 100w QPS，怎么扩展？

**答**：单机到顶了就**水平扩展**：① 网关层**无状态**（规则从配置中心拉、计数在 Redis），直接加机器 + 负载均衡；② Redis 用**集群模式**分片；③ 本地缓存命中率优化（布隆过滤器预过滤）；④ 特征提取并行化。核心思路：**先单机榨干（epoll + 本地优先 + 异步），再横向扩展（无状态 + Redis 集群）**。

---

### 28. 发现一个正常用户被误杀了，怎么排查？

**答**：① 查日志——根据 userId 查 RiskEvent（里面有完整决策上下文：触发规则、评分、特征值）；② 看特征——这个用户的特征向量是不是某个特征异常了；③ 看规则——触发的规则阈值是不是设太严了；④ 临时止血——把用户加白名单，立刻恢复；⑤ 长期修复——调规则阈值/特征权重，避免再犯。

**追问：怎么证明决策是对的（用户投诉时）？** RiskEvent 里有完整的触发规则、评分、原因（reason 字段），这就是证据——这也正是"可解释风控"的价值：能回答"为什么拦你"。
