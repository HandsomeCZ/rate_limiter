# 高并发 API 网关（Reactor + 限流风控）代码优化分析报告

> 分析范围：`https-gitee-com-czishandsome-tcp-server-2/`（Reactor 网络层）+ `rate_limiter/`（限流/风控业务层），共约 7800 行 C++17。
> 所有修复均已通过 **MinGW g++ 8.1.0 编译**、**10 个单元测试全部通过**、**HTTP 服务端到端冒烟测试通过**。

## 一、已修复的问题（按严重程度排序）

### 1. 致命正确性 Bug

| # | 位置 | 问题 | 修复 |
|---|------|------|------|

## 二、已发现但**未修改**的问题（建议，供面试阐述）

> 以下问题改动较大或需权衡，未在本轮直接修改，但面试中主动提到会显著加分。

### A. TimerWheel（时间轮）设计缺陷
- `net/src/TimerWheel.cpp`：`pos = (_tick + delay) % capacity`，**delay ≥ capacity（60s）时环绕错误**（如 120s 超时实际 60s 触发）。当前默认 60s 恰好正确，属于「碰巧能用」。
- 超时回调在 `~TimerTask()` 析构中触发，语义隐晦；`Refresh` 只往新槽 push 而旧槽不删除，依赖 shared_ptr 引用计数兜底，脆弱。
- `TcpServer::enableConnectionTimeout` 用 `std::hash<std::string>(connName)` 作为定时器 ID，理论上存在哈希碰撞。
- `TcpConnection::refreshTimeout()/cancelTimeout()` 是**空实现**（注释写着「由 TcpServer 层处理」），误导性强。

### B. 单机 10w QPS 的伸缩性瓶颈（真实压测会暴露）
- `LocalRateLimiter` 用**单个全局 mutex** 保护所有窗口，高并发下是争用热点 → 建议按 key 分片（如 64 个分片锁）。
- 热路径存在大量**内存分配**：`Request` 三个 `std::string` 拷贝、`KeyBuilder::build` 用 `ostringstream` 拼 key、每个 `Feature` 含 3 个 string、`WriteResponse` 用 `ostringstream` 拼响应再 `send()` 复制。
- `StaticFeatureExtractor` 每个请求都调用 `localtime_r/localtime_s`（每小时才变化，可缓存）。
- `findFeature` 线性扫描 + 字符串比较（特征/规则数量小时可接受）。

### C. 死代码 / 未接线
- `RateLimiterFacade`（Redis 分片限流门面）**从未被实例化**，HTTP 服务实际走 `LocalRateLimiter`。
- `RuleEngine` 类基本是死代码（LocalCache 自己做了规则匹配），仅单测使用。
- `RedisConnection::isAlive()`、`SlidingWindowAggregator::advanceBucket`（声明未定义）等未使用。

### D. 其他
- `RuleHandler::handle()` 注释称「命中短路」，实际**不短路**（白名单命中仍继续执行后续 handler）。
- `QPSTracker::getCount()` 在警戒区调用 `fixedWindowIncr`（**带副作用**：把「读计数」变成了「写+读」）。
- `InetAddress` 仅支持 IPv4。
- `main.cpp`：`new` 出来的对象不释放（cleanup 代码不可达）、`signalHandler` 里调 `std::cout`/`exit()`（非异步信号安全）。
- `RedisConnectionPool::init()` 中途失败会泄漏已建连接。
- `RedisConnection::exec` 用 `%s` 格式化（非 `%b`，key 含空格/二进制会出错）。
- `SlidingWindowAggregator` 的 bucket reset（加锁）与 add（无锁）在秒切换瞬间仍可能丢一次计数（原子操作无 UB，仅统计误差）。
- `send(const std::string&)` 跨线程路径通过 `std::bind` 复制整串（本服务单线程每连接，未触发；多线程生产者场景建议用 `shared_ptr<string>`）。

## 三、面试讲解要点（可主动抛出）

1. **`Buffer::readFd` 为什么用 readv + 栈缓冲？** 答：① 避免 `writable==0` 时 0 字节 recv 被误判为对端关闭；② 一次系统调用读满 64KB，减少大报文下的 read 次数。这是 muduo 的经典做法。
2. **本地限流为什么要「增量同步」Redis？** 答：若同步全量窗口计数，100ms 一次会把计数放大 ~10 倍，破坏跨机一致性；增量同步保证最终一致。
3. **熔断器为什么要「半开探测」？** 答：纯 fail-open 会导致熔断后永远无法自愈（失败计数无路径清零）；冷却超时后放一次探测请求，成功则恢复、失败则继续熔断。
4. **Reactor 里 Accept 为什么循环 accept？** 答：level-triggered 下每个事件只 accept 一个会导致突发建连积压，循环直到 EAGAIN 把就绪队列一次性清空。
5. **HTTP 解析为什么要设上限？** 答：防 slowloris / 超大请求耗尽内存（memory DoS）。
6. **跨线程状态为何要 `shared_lock`？** 答：读多写少场景（规则 1s 刷新一次）用读写锁，避免读路径争抢，同时保证 `match` 与 `loadRules` 不数据竞争。

### 新增建议（未改，较大改动需权衡）

- `LocalRateLimiter` 本地滑窗 / Redis ZSet / 同步 INCRBY 三种计数**语义不一致**（本质是「本地↔Redis 混合计数」设计缺陷），建议统一为单一计数源。
- `QPSTracker::getCount` / `syncToRedis` 在**持全局锁期间做 Redis 网络 I/O**（最长 200ms 超时），会阻塞所有请求的 QPS 特征提取 → 锁外做 I/O 或用无锁结构。
- `Socket::bind` 用 `assert`（`NDEBUG` 下失效），`listen` 返回值被忽略 → 端口占用等失败被静默吞掉。
- `Acceptor` 未处理 `EMFILE`（fd 耗尽），level-triggered 下会**忙轮询**（经典解法：预开一个 idle fd 占位）。
- `epoll_ctl` 返回值被忽略，失败时 `channels_` 与内核 epoll 集合不一致 → I/O 静默丢失。
- `TcpConnection::state_` 普通枚举被跨线程读写（单线程每连接场景影响小）。
- `RedisClient::fixedWindowIncr` 忽略 `EXPIRE` 返回值；`isAvailable()` 只查连接池空闲数而非连接存活。

## 七、进阶优化（第二轮：锁分片 / 时间轮重写 / 热路径去分配）

### A. `LocalRateLimiter` 锁分片（支撑 10w QPS）

- **问题**：单一全局 `mutex` 保护所有窗口，10w QPS 下所有线程争同一把锁。
- **修复**：拆成 **64 个分片**，按 `hash(key) % 64` 路由，每个分片独立 `unordered_map + mutex`。
- **附带修复**：警戒区的 Redis `slidingWindowCheck`（网络 I/O）从**锁内移到锁外**，避免长事务阻塞其它请求；同步线程先在各分片锁内收集增量、再在锁外做 Redis I/O。

### B. TimerWheel 重写（修环绕 bug + 去 hash ID）

- **问题**：`pos = (_tick + delay) % capacity`，`delay ≥ capacity`（60s）时环绕提前触发；用 `std::hash<string>` 做定时器 ID 有碰撞风险；回调在 `~TimerTask` 析构里触发，语义隐晦且造成析构 use-after-free。
- **修复**：
  1. 改用**绝对 deadline**（`deadline = _tick + delay`，`_tick` 单调递增），触发条件 `deadline <= _tick`，支持任意 delay 的多轮，不再环绕。
  2. ID 改为**原子计数器** `_nextId.fetch_add(1)` 分配。
  3. 回调**显式触发**（`processSlot` 里调用），`TimerTask` 变成纯数据结构，析构无副作用、无 UAF。
  4. `refresh` 改为「作废旧任务 + 新建任务」（惰性删除），不再依赖 shared_ptr 引用计数兜底。
- **验证**：独立测试 1s/3s 定时器按时触发，12s 定时器（> capacity 10）5 秒内不误触发。

### C. 热路径去分配（`KeyBuilder` / `buildKey`）

- **问题**：`KeyBuilder::build` / `buildShard` / `LocalRateLimiter::buildKey` 用 `ostringstream` 拼 key，热路径每次请求都触发多次堆分配。
- **修复**：改为 `std::string::reserve` + `append`，并加 `appendU32` 用栈缓冲做整数转字符串（避免 `std::to_string` 分配）。
- **验证**：单测 `KeyBuilder produces expected key format` 通过，格式不变。
